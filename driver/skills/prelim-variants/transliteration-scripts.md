# Transliteration scripts — reference

Non-Latin scripts to consider when the jurisdiction scope is multi-region or worldwide. Generated by Claude directly during Step 5 of `prelim-variants`. Verification is a human step when transliterations produce hits.

## When to generate

| Jurisdiction scope | Scripts to generate |
|---|---|
| **Worldwide / global** | All 8 below |
| **EU-wide** | Cyrillic (for Russia / Bulgaria / etc.) and Greek (Greece / Cyprus) — most marks register in Latin scripts |
| **Asia-Pacific** | Hanzi (Chinese), Katakana (Japanese), Hangul (Korean), Thai (Thailand) |
| **MENA** | Arabic |
| **Indian subcontinent** | Devanagari (Hindi) |
| **US / UK / single-Latin-script jurisdiction** | None — skip unless the mark is itself non-Latin |

For specific country lists, the orchestrator passes the jurisdiction list through; this reference covers the major scripts only.

## The 8 scripts

### Chinese (Hanzi / 汉字)

- **Approach:** generate both a phonetic transliteration AND a meaning translation, since Chinese can use either
- **Phonetic example:** "Lumengarde" → 艾佛莱特 (Ài fó lái tè) — sound-alike using common transliteration characters
- **Meaning example (a SET, never one guess — see the rule below):** "Lumengarde" → 永光 · 长明 · 恒光 (everyday "everlasting light" first, then literal/adjacent) — derive the set from the concept, do not template these characters
- **When to use phonetic:** when the brand is itself a coined / non-translatable word (Nike, Aureon)
- **When to use meaning:** when the brand has clear English semantic content (Apple, Lumengarde)
- **Meaning = the everyday-word-first equivalence SET, never one technical guess** (this *supersedes* the earlier "specific concept only / drop the everyday word" rule). Generate the small deterministic SET of natural-language renderings of the concept, **common-usage first**, then technical, then adjacent — e.g. COLORA → CN **色彩, 颜色** (everyday "colour") · **色度** (technical "chromaticity") · **彩度 / 色相** (adjacent) — tagging each member's register (everyday | technical | adjacent). **Never drop the everyday word because it looks saturated.** A saturated everyday-word count is the signal to *narrow to the field*, not to abandon the word: the register layer scopes the saturated token to the matter's filed in-scope Nice classes (a structured class × region filter — the token stays the substring predicate; goods-vocabulary words are never ANDed into the search text) and enumerates that (see [`prelim-register` register-recipes.md](../prelim-register/register-recipes.md) saturated-field handling). The everyday word is exactly what local registrants file and what the reviewing lawyer searches, so a common word is never grounds to skip it — or to drop a live in-class hit behind it. (Dropping the everyday word dodges the saturation noise but discards the real conflict hiding in the crowd.)
- **Risk:** Chinese mark registrations sometimes file BOTH. Always generate both for high-tier matters
- **Verification:** Claude generates plausibly but the reviewing lawyer or local counsel should confirm before any output reaches the client

### Japanese (Katakana / カタカナ)

- **Approach:** Katakana is THE script for foreign brand names in Japan. Hiragana / Kanji rare for non-Japanese marks
- **Example:** "Lumengarde" → エバーライト (ebārait̄o)
- **Example:** "Level" → レベル (reberu)
- **Notes:** Katakana phonetic rules are predictable. Long vowels marked with ー. The "L" sound becomes "R" (and vice versa).
- **Verification:** Pattern is mechanical enough that Claude's output is generally reliable; flag for human confirmation on hits

### Korean (Hangul / 한글)

- **Approach:** phonetic transliteration following Korean Romanisation rules
- **Example:** "Lumengarde" → 에버라이트 (ebeoraiteu)
- **Example:** "Level" → 레벨 (rebel)
- **Notes:** "V" → "ㅂ" (b sound). "L" maps to "ㄹ" mid-word, "ㄹㄹ" at consonant clusters. Final stops get the silent "ㅡ" vowel
- **Verification:** flag for human confirmation on hits — Korean transliteration is less mechanical than Katakana

### Arabic (الأبجدية العربية)

- **Approach:** phonetic transliteration following Arabic abjad rules
- **Example:** "Lumengarde" → إيفرلايت
- **Example:** "Level" → إليفيت
- **Notes:** Arabic doesn't write short vowels in the abjad — transliterations include them via the long-vowel letters (ا ي و) and matres lectionis
- **Verification:** Arabic transliteration has multiple valid spellings (same sound, different characters). Always flag for human confirmation; consider running multiple plausible transliterations

### Cyrillic (Кириллица)

- **Approach:** phonetic transliteration following Russian Cyrillic conventions
- **Example:** "Lumengarde" → Эверлайт
- **Example:** "Level" → Элевейт
- **Notes:** "W" → "В". "Th" → "С" or "Т". "H" sometimes silent, sometimes "Х". Bulgaria and other Cyrillic-using countries may have slight variations
- **Verification:** flag for human confirmation on hits

### Devanagari (Hindi / देवनागरी)

- **Approach:** phonetic transliteration following Hindi conventions
- **Example:** "Lumengarde" → एवरलाइट
- **Example:** "Level" → एलिवेट
- **Notes:** Vowels carried by matras attached to consonants. English "V" can be व or भ depending on regional preference
- **Verification:** flag for human confirmation on hits

### Thai (อักษรไทย)

- **Approach:** phonetic transliteration following Thai loanword orthography
- **Example:** "Lumengarde" → เอเวอร์ไลท์
- **Example:** "Level" → เลเวล
- **Notes:** Thai is an abugida — vowel signs attach around the consonant (before, after, above or below it), so a transliteration is not a letter-for-letter mapping. Final consonants that are silent in the source word carry the ์ (thanthakhat) silencer, which is why English "-ght" and "-r" endings survive in the spelling but not the sound. Written without spaces between words; tone marks are conventionally omitted in brand transliterations
- **Verification:** flag for human confirmation on hits — the same English sound admits several accepted Thai spellings, and Thai brand registrations frequently file more than one

### Greek (Ελληνικό αλφάβητο)

- **Approach:** phonetic transliteration following Modern Greek orthography
- **Example:** "Lumengarde" → Εβερλάιτ
- **Example:** "Level" → Λέβελ
- **Notes:** Digraphs matter more than single letters. The "B" sound is **μπ** (β on its own is "V"); "D" is **ντ**; "G" is **γκ**. So a Latin "B" almost never maps to the visually similar β. English "-ight" → **-άιτ**. A Greek word carries **one** accent — don't stack them
- **Verification:** flag for human confirmation on hits

## Generation rules

1. **One PHONETIC transliteration per script per mark element.** Don't generate exhaustive phonetic variant sets within a single script — pick the most likely. (Meaning translations are the exception — see 2b.)
2. **For Chinese: generate phonetic AND meaning translations** for any mark with clear semantic content. One entry (phonetic only) for coined marks.
2b. **Meaning translation = the everyday-word-first equivalence SET (it reverses the older "specific concept, drop the everyday word" rule).** Emit the small deterministic set common-usage first, then technical, then adjacent — one manifest row per member, each tagged with its register (everyday | technical | adjacent). **Never drop the everyday word for looking saturated:** saturation is handled downstream by class-scoped enumeration in the register layer ([register-recipes.md](../prelim-register/register-recipes.md)) — the token narrowed to the filed in-scope Nice classes, not by ANDing goods words into the query and not by abandoning the word. A common everyday word is never grounds to skip a meaning rendering or to drop a live in-class hit behind it.
3. **Tag the variant row** in the Variants table with the category `translit-<script>` (e.g. `translit-cjk-japanese`, `translit-arabic`) and a rationale explaining whether it's phonetic or meaning-based. **For Chinese the category token MUST carry the sense** — `translit-zh-meaning` for a meaning translation, `translit-zh-phonetic` for a phonetic one — because the downstream saturation / class-scoped-enumeration gates key on the `translit-*-meaning` tag; a meaning row tagged only `translit-zh` would silently skip the field-narrowing and revert to the old drop-on-saturation behaviour.
4. **Flag for verification** by putting `✅` in the Variants table's `Verify?` column for every transliteration row. The downstream skill marks any HIT against these variants as needing reviewer sign-off before inclusion in the deliverable.
5. **Every non-Latin row carries its ROMANISATION, on its own row** — `"romanization"` in the manifest's structured sibling, and the Latin form in parentheses in the prose row's rationale. This is not decoration: **half the registers we search hold a non-Latin filing ONLY under its transliteration and cannot answer the characters at all.** A row without one is a term that can be searched on some providers and on no others — and the one that refuses it is right to, because searching the characters there returns 0 with no error and reads as a clean. (A clearance run on 2026-07-29 compiled thirteen native-script terms with no romanisation; every one was refused and the transliteration axis produced no coverage.) Rules: plain ASCII letters and digits, syllable-separated by single spaces, no tone marks and no diacritics (华威豹 → `HUA WEI BAO`, ティキスラッシュ → `TIKI SURASSHU`, 티키 슬러시 → `TIKI SEULLEOSI`, Тики Слаш → `TIKI SLASH`); the romanisation goes on the row whose own value it romanises, never on a neighbour and never as a row of its own; and a value that is already Latin never gets one. The driver puts BOTH forms on the search entry and each provider expresses the one its index holds — you state the pair, you never choose which gets searched.

## When transliteration is overkill

Skip transliteration for:
- Single-jurisdiction searches in a Latin-script country
- Internal sanity-check / brainstorm runs (the standalone mode of `prelim-variants`)
- Matters where the client explicitly excludes non-Latin markets

When in doubt: generate them. Cost is one extra dozen rows in the variant manifest, but missing a Japanese katakana hit on a global launch is the kind of miss that gets noticed post-launch.

## What this DOESN'T cover

- Trade name vs trademark distinctions in non-Latin markets (handled by local counsel)
- Honorific / corporate-suffix conventions (Pvt Ltd in India, AG in German, GmbH in German, K.K. in Japan)
- Right-to-left text rendering for Arabic in the deliverable Excel — output handling is in `prelim-search`'s Excel writer
- Native-language semantic equivalents that aren't transliterations (e.g., the Chinese meaning SET 永光 · 长明 is a TRANSLATION, not a transliteration — but we include both under this file's umbrella for practical reasons)
